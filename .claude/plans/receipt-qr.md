# Импорт позиций чека по QR-коду

Задача в `tasks.md` → «Импорт чека по QR». Обсуждено с пользователем 2026-10-04, кода пока нет.

> **Делается после миграции на MongoDB** (`mongo-migration.md`, приоритет). Всё, что ниже
> сказано про Firestore/Firebase Admin/`firestore.rules`, на новой архитектуре заменяется на:
> эндпоинт в общем `server/`, проверка premium по `users` в Mongo, коллекция `receipts` в Mongo,
> атомарная запись чека и операций — транзакция Mongo на сервере, доступ — общий middleware
> владелец/участник.

## Принятые решения
- **Источник данных — proverkacheka.com** (платный агрегатор поверх ФНС, документированный API,
  авторизация токеном). Выбран как самый быстрый старт.
  - Официальный партнёрский API ФНС бесплатен и правилен для коммерческого продукта, но требует
    ИП/юрлица. У пользователя их пока нет — вернуться к нему, когда появятся.
  - Отвергнут ofd.ru: это один конкретный ОФД, он видит только чеки своих касс. Тестовый чек
    («МРИЯ-ФАРМ», Мариуполь, ФН 7380440903668629, ФД 11963, ФП 0112147175) на check.ofd.ru
    не найден. Его официальный API к тому же для продавца, а не покупателя.
  - Неофициальный API мобильного приложения ФНС — только запасной вариант: каждый пользователь
    должен логиниться в ФНС, API может сломаться без предупреждения.
  - Тот же чек распознало приложение WebMoney вместе с позициями — значит, чеки новых регионов
    (ДНР) в ФНС есть, риск покрытия снят.
- **Чек разбивается на операции по категориям**: позиции группируются по `categoryId`, на каждую
  группу — одна `expense`-транзакция (сумма группы), все связаны через `receiptId`. Отчёты и
  дашборд продолжают работать по `categoryId` транзакции без изменений, детализация по позициям
  живёт в `Receipt`. Операция на каждую позицию отвергнута: засоряет журнал.
- **Premium-фича** — каждый запрос к API платный.

## Что лежит в QR
Фискальный QR не содержит позиций, только реквизиты для поиска в ФНС:
`t=20261002T1346&s=1678.86&fn=7380440903668629&i=11963&fp=0112147175&n=1`
- `t` — дата/время, `s` — сумма, `fn` — ФН, `i` — ФД, `fp` — ФП;
- `n` — тип расчёта: 1 приход, 2 возврат прихода, 3 расход, 4 возврат расхода.

## Архитектура

### 1. `server/` — прокси на VPS (новый workspace) `[server]`
Прокси нужен, потому что токен proverkacheka секретный и платный — в клиентский бандл его класть
нельзя. Плюс CORS. Cloud Functions не используем: Spark-план, исходящие запросы там запрещены.
Тот же бэкенд потом пригодится под webhook подписки (`tasks.md`, «Единый Firebase-проект» п.4).
- Node + TS (Fastify или Express), systemd-сервис; nginx проксирует `/flowledger/api/*`.
- `POST /api/receipts/fetch` принимает `{ qrraw }` и `Authorization: Bearer <Firebase ID token>`.
  - Проверка токена — `firebase-admin` `verifyIdToken` (работает на Spark).
  - **Проверка premium**: читаем `plan` владельца базы (`users/{uid}.activeOwnerId`, иначе сам
    `uid`) через Admin SDK.
  - Лимит запросов на пользователя в сутки (защита от расхода платных запросов).
  - Ответ — нормализованный `NormalizedReceipt`, не сырой формат proverkacheka.
- Интерфейс `ReceiptProvider.fetch({ fn, fd, fp, t, s, n }) → NormalizedReceipt`. Первая
  реализация — proverkacheka; позже — официальный API ФНС без переделки остального.
- Нормализация на сервере:
  - копейки → рубли с округлением до копеек;
  - **выкидывать персональные данные** (ФИО покупателя и кассира);
  - коды ответа proverkacheka → статусы (`loaded` / `pending` — ФНС ещё не получила чек /
    `not_found` / `error` / превышен лимит).
  - Формат API (endpoint, поля, коды ответа) **сверить с документацией при реализации**: в
    песочнице сессии домен был заблокирован, описание было по памяти.
- Firestore сервер **не пишет** — только возвращает данные. Запись делает клиент по обычным
  Security Rules: не нужны Admin-креды с правом записи, правила не обходятся.
- Деплой — отдельный workflow `deploy-server.yml` по образцу `deploy.yml` (rsync +
  `systemctl restart`). Токен proverkacheka и сервис-аккаунт Firebase (только чтение
  `users`) — в GitHub Secrets / env на сервере.

### 2. Модель данных `[interfaces]`
```
Receipt {
  id                  // детерминированный `${fn}_${fd}_${fp}` — защита от двойного импорта
  userId, createdBy, createdAt
  qrraw, fn, fd, fp, dateTime, totalSum, operationType   // operationType = n из QR
  seller { name, inn, address }
  items: ReceiptItem[]          // массив внутри документа, чеки обычно < 100 позиций
  status: 'pending' | 'loaded' | 'not_found' | 'error'
  walletId
  transactionIds: string[]
}
ReceiptItem { name, price, quantity, sum, nds?, categoryId? }
```
- `Transaction.receiptId?` — новое поле.
- Тип операции из `n`: 1 → `expense`; 2 (возврат прихода) → `income`; 3/4 — редкость для
  личного учёта, на первом этапе так же по знаку (3 → `income`, 4 → `expense`).
- Детерминированный id включает только фискальные реквизиты. Внутри одной базы (`userId`)
  нужна проверка существования до записи. Открытый вопрос: класть ли `userId` в id документа,
  чтобы один и тот же чек могли импортировать разные базы.

### 3. `shared` `[shared]`
- `lib/receiptQr.ts` — парсинг и валидация строки QR (используется и для ручного ввода).
- `repositories/receipts.repo.ts`:
  - `createReceipt` — дедупликация по id: при дубле возвращает «чек уже добавлен».
  - `commitReceipt` — пишет `Receipt` + N транзакций (по одной на категорию) **атомарно**,
    баланс кошелька — через ту же дельта-логику, что `walletDeltas` в `transactions.repo.ts`.
    `runTransaction` придётся расширить до нескольких операций за раз. **Главное техническое
    место плана.**
  - `deleteReceipt` — каскадно удаляет транзакции (как `deleteDebt`).
- `hooks/useReceipts.ts`, `useFetchReceipt` (react-query mutation на прокси).
- `firestore.rules` — коллекция `receipts` по паттерну `hasAccess`. Деплоить отдельно через
  `deploy-firestore-rules.yml`.

### 4. UI `[client]`
1. Кнопка «Сканировать чек» в журнале / модалке добавления. Для free-плана — заглушка
   «доступно в Premium».
2. Сканер, три пути ввода:
   - камера: нативный `BarcodeDetector` (Chrome Android), фоллбэк — `qr-scanner` /
     `@zxing/browser` (iOS Safari `BarcodeDetector` не поддерживает);
   - загрузка фото чека из галереи;
   - ручной ввод ФН/ФД/ФП/даты/суммы.
3. Предпросмотр:
   - продавец, дата, позиции, итог;
   - выбор кошелька;
   - категория на весь чек, переопределяется у отдельных позиций чипами;
   - «Сохранить».
4. Статус `pending` (ФНС ещё не получила чек, бывает до суток) — сохраняется с кнопкой
   «Повторить», без автоматических фоновых повторов на первом этапе.
5. В журнале у операции с `receiptId` — значок чека; по тапу — список позиций.

Стиль — только неоморфные примитивы (`memory.md` → «Правила стиля»).

### 5. Автокатегоризация (второй этап)
Коллекция `categoryRules`: ИНН продавца или ключевое слово в названии позиции → `categoryId`.
Правило запоминается из ручных выборов пользователя.

### 6. `mobile` (позже) `[mobile]`
`expo-camera` (встроенный сканер штрихкодов), `shared`-слой общий.

## Порядок работ
1. Зарегистрироваться на proverkacheka.com, получить токен, сверить формат API и тариф.
   Проверить тестовый чек вручную.
2. `server/` — прокси, проверка Firebase-токена и premium, лимиты, деплой на VPS, nginx.
3. `interfaces` + `shared` — типы, парсер QR, репозиторий с атомарной записью, правила.
4. `client` — сканер, предпросмотр, сохранение, просмотр чека из журнала.
5. Автокатегоризация.
6. `mobile`.

## Решено 2026-10-04
- **Premium проверяется у владельца базы** (`activeOwnerId`, иначе сам пользователь):
  premium покупается на базу, участники общего доступа пользуются им.
- **Тестирование premium** до интеграции подписки — пользователь вручную выставляет себе
  `plan: 'premium'` в `users/{uid}` через Firebase Console.

## Открытые вопросы
- Конкретные значения лимитов (запросов в сутки на пользователя) — после выяснения тарифа.
- Возможная миграция Firestore → собственная MongoDB (обсуждается 2026-10-04): если решится,
  прокси из п.1 становится полноценным API-бэкендом, а `receipts` сразу заводится в Mongo, а не в
  Firestore.
