# Инструкции для Claude

- Всегда отвечай только на русском языке.
- Явные инструкции пользователя (о стиле работы, коммуникации и т.п.) сохраняй сюда как постоянные
  правила, а не только для текущей сессии.
- При создании новой сессии/ветки для задачи — не называть ветку сразу по первому сообщению/приветствию
  сессии. Дождаться, пока станет известна конкретная задача от пользователя, и только тогда называть
  (или переименовывать выданную) ветку по теме этой задачи.
- **Деплой и мердж в `main` — две независимые операции, не путать одно с другим.**
  - Мердж в `main`: всегда через Pull Request (через GitHub) — не мерджить напрямую локальным
    `git merge`/`git push` в `main`, даже при fast-forward и даже в конце сессии. Это правило не
    зависит от того, был деплой или нет.
  - Деплой: можно в любой момент запускать на текущей рабочей ветке — без мерджа и без PR в
    `main`. Мердж сам по себе не обязывает отдельно катить деплой: если эта же ветка уже была
    задеплоена и код с тех пор не менялся, повторно дёргать деплой вручную после мерджа не нужно
    (push в `main` всё равно автоматически прогонит `deploy.yml`/`deploy-firestore-rules.yml` по
    своим путям — это штатно, не задваивать искусственно ещё одним ручным запуском).
  - Механика ручного деплоя ветки: у `.github/workflows/deploy.yml` (клиент,
    `client/**`/`shared/**`/`interfaces/**` → VPS) и `.github/workflows/deploy-firestore-rules.yml`
    (`firestore.rules`/`firestore.indexes.json` → Firebase) есть триггер `workflow_dispatch` —
    запускать вручную на нужной ветке (`gh workflow run <файл> --ref <ветка>` или GitHub MCP
    `actions_run_trigger` method `run_workflow` с `ref: <ветка>`). Оба workflow деплоят в тот же
    прод (общий VPS-путь `/flowledger`, тот же Firebase-проект `flowledger2`), отдельного
    staging-окружения нет — деплой ветки временно подменяет то, что видят пользователи на проде,
    до следующего деплоя.
  - Перед деплоем клиента проверять сборку ровно той же командой, что гоняет CI — `npm run
    build:client` из корня (`tsc -b && vite build`), а не `npx vite build` напрямую внутри
    `client/`. `vite build` сам по себе на esbuild и не делает полной проверки типов по project
    references между workspace'ами (`client`/`shared`/`interfaces`) — пропускает ошибки, которые
    ловит `tsc -b`. Один раз это привело к тому, что два деплоя подряд падали на шаге сборки в CI
    (тип пропал у поля после правки `NAV_ITEMS`), а на проде тихо оставалась старая версия без
    вообще каких-либо признаков ошибки — пользователь решил, что фичи просто не задеплоились.
    После любого пуша, где менялись `client`, `shared` или `interfaces`, гонять `npm run
    build:client` из корня перед `workflow_dispatch`, и после деплоя проверять `conclusion` самого
    workflow run (`actions_get`/`actions_list`), а не только факт, что он был запущен (`queued` —
    не значит успех).
  - Не отслеживать сам ход выполнения деплоя без явной просьбы пользователя — не гонять цикл из
    нескольких `sleep`/пере-проверок статуса подряд с промежуточными сообщениями "ещё выполняется".
    Запустить `workflow_dispatch`, один раз выждать типичное время выполнения и проверить итоговый
    `conclusion` — этого достаточно, чтобы поймать провал сборки (см. правило выше). Активно
    наблюдать за прогрессом (несколько проверок подряд, промежуточные статусы) — только если
    пользователь явно попросил последить/подождать деплой.
  - Деплой клиента (`deploy.yml`) и деплой правил Firestore (`deploy-firestore-rules.yml`) —
    **раздельные** workflow, `workflow_dispatch` одного не запускает другой. Если в коммите
    менялся `firestore.rules` (например, новая коллекция) — обязательно дёргать
    `deploy-firestore-rules.yml` тем же `ref` отдельно, помимо `deploy.yml`. Забыть это —
    типичная причина "Missing or insufficient permissions" в проде: клиент уже знает про новую
    коллекцию, а Firestore ещё живёт по старым правилам без разрешения на неё. Один раз именно
    так и вышло — задеплоил только клиент, забыл про правила.

## Контекст проекта — с чего начинать

Рабочий контекст (архитектура, задачи, план-доки) вынесен из корня в `.claude/`, чтобы не раздувать
корень репозитория и не тащить в каждую сессию закрытые темы. Порядок чтения:

1. `.claude/memory.md` — архитектура, принятые решения, стиль, текущий стек. Читать в начале любой
   содержательной сессии.
2. `.claude/plans/tasks.md` — активные задачи и открытые пункты. Что реально нужно сделать сейчас.
3. `.claude/plans/*.md` — план-доки по темам, ещё не полностью закрытым (контекст решений, на
   которые ссылается tasks.md).
4. `.claude/archive/` — закрытые темы и полностью выполненные задачи. Открывать точечно, только
   если явно нужен исторический контекст — не читать по умолчанию.

## Структура `.claude/`

```
.claude/
├── memory.md                    — архитектура и решения (живой документ)
├── plans/                       — активный контекст
│   └── tasks.md                 — текущие открытые задачи
└── archive/                     — закрытые темы, не грузить в контекст без необходимости
    ├── plans/
    │   ├── 00-initial-setup.md      — первичный scaffold, выполнено и неактуально
    │   ├── 01-firebase-pivot.md     — пивот на общий Firestore, заменён BYO-Firebase, затем
    │   │                              реверчен обратно (см. single-project-pivot.md)
    │   └── 02-byo-firebase.md       — план BYO-Firebase, реверчен на единый проект
    └── tasks/
        ├── initial-scaffold.md      — закрытые задачи начального scaffold
        ├── byo-firebase-core.md     — закрытые задачи базовой реализации BYO-Firebase (реверчено)
        └── single-project-pivot.md  — реверт BYO-Firebase на единый проект (актуальная архитектура)
```

(`mobile/.claude/settings.json` — отдельная область, конфиг плагина Expo для mobile-подпроекта,
к этой структуре контекста не относится.)

## Контекст по workspace'ам

У каждого npm workspace — свой короткий `CLAUDE.md` в его корне: `client/CLAUDE.md`,
`mobile/CLAUDE.md`, `shared/CLAUDE.md`, `interfaces/CLAUDE.md`. Claude Code подхватывает его
автоматически при работе внутри этой директории. Каждый такой файл — не дубликат
`memory.md`/`tasks.md`, а указатель: роль workspace'а в двух-трёх предложениях + ссылка сюда и в
`.claude/plans/tasks.md`, отфильтрованная по тегу этого workspace (`[client]`, `[mobile]`,
`[shared]`, `[interfaces]` — теги проставлены прямо в пунктах `tasks.md`).

При заведении нового workspace — заводи для него такой же `CLAUDE.md` по этому шаблону, а новые
задачи в `tasks.md` сразу помечай тегом (можно несколькими, если фича сквозная).

## Правило поддержания структуры

Когда пункт в `.claude/plans/tasks.md` или план-док в `.claude/plans/` полностью закрыт и больше не
нужен как активный контекст — переноси его (или его закрытые подзадачи) в `.claude/archive/` по той
же структуре: план-доки → `archive/plans/`, закрытые группы задач — новым или дополненным файлом в
`archive/tasks/` по теме. Не удаляй историю — переноси, чтобы её можно было поднять точечно, но по
умолчанию она не читалась и не раздувала контекст. При переносе обновляй перекрёстные ссылки в
переносимом файле и в файлах, которые на него ссылаются (`memory.md`, `tasks.md`, соседние план-доки).
